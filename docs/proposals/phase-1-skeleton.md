### Job runner model (ING-1, ING-3, LOAD-3)

Two options; the recommendation follows the module design in section 9.

| | A. Long-running consumer on Fargate | B. Fargate task per scheduled run |
|---|---|---|
| Shape | One ECS service polls SQS; each message is one stage for one item. EventBridge Scheduler sends a "poll due sources" message every N minutes. | EventBridge Scheduler starts an ECS task that runs the whole pipeline for due sources, then exits. |
| Retries | Per stage, by SQS redelivery and DLQ. | Per run; a failed item waits for the next run unless the task tracks it. |
| Cost | One small task always on (scale to zero outside polling windows is possible). | Pay per run; minutes of start-up per task. |
| Fit | Matches ING-1 "staged, retryable" and LOAD-3 "Background work uses SQS". | Simpler, but retries per stage need their own bookkeeping. |

Chosen: A (ADR-0008 accepts the section 9 design).

### Extraction libraries (heading-preserving, ING-1)

Moments need heading text, heading level, and the publisher's heading `id` for anchor links (§3.2). Two options:

| | 1. trafilatura + lxml anchor pass | 2. readability-lxml + lxml |
|---|---|---|
| Main-content detection | Strong on blogs and news; well maintained. | Port of Mozilla Readability; good on articles, weaker on docs-style pages. |
| Headings | Kept in its XML/Markdown output, but original `id` attributes are not kept. A second lxml pass over the original HTML maps extracted headings to ids by text match. | Returns cleaned HTML that keeps the original elements, so ids survive. |
| Risk | Text-match mapping fails when headings repeat or are rewritten. | More boilerplate leaks into the content; the library is less active. |

Either way, a fixture set from real seed sources (P1-W2-S05) decides it. Needs owner choice after that test.

## 5. CI

Provider: GitHub Actions (ADR-0009).

Every PR runs, in parallel jobs:
1. Format check: `prettier --check`, `ruff format --check`.
2. Lint: `eslint`, `ruff check`.
3. Typecheck: `tsc --noEmit` per TS package, `pyright`.
4. Tests: Vitest, pytest, with a Postgres + pgvector service container.
5. Migration check: apply all migrations to an empty DB, regenerate TS and Python types, fail on any diff (ADR-0002). Fail if a merged migration file changed.
6. `cdk synth` for prod (the only AWS environment, Q-P1-28), plus CDK assertion tests.

No deploy job. The owner deploys (CLAUDE.md).

How hooks mirror CI locally:
- `.claude/hooks/format-and-lint.sh` runs steps 1–2 on each edited file.
- `.claude/hooks/typecheck-changed.sh` runs step 3 for the packages with changed files at the end of each turn.
- `pnpm check` (section 8) runs steps 1–5 locally before the owner commits.

## 6. Observability (OPS-2, minimum for Phase 1)

## 9. Module map

Two whole-shape candidates were sketched independently and screened for shallow modules, information leakage, split ownership, two ways to do one task, importable internals and hand-synced lists.

- **Candidate 1 (rejected): ranking and notes in the web app.** TS ranks on request with a TS precompute job; both languages call models, each through its own budget wrapper. Fails the screen: two writers of the AI cost ledger (split ownership of OPS-4), two AI-3 storage paths, and REC-2's later learned model would be rewritten in Python (ARCH-2 "Nothing gets written twice").
- **Candidate 2 (base): Python owns every model call and the ranker; TS owns requests, sessions and reads.** ARCH-2 gives "ingestion, ML, and AI jobs" to Python; CACHE-1 makes the feed a precompute, which is a job, not request work.

### Ingestion job flow (job runner option A)

- EventBridge Scheduler sends one `reconcile.tick` to SQS every 5 minutes. Per-source cadence (`next_poll_at`, `poll_interval`) lives in Postgres (ING-3), so polling has one owner instead of ~100 EventBridge schedules.
- Queues: `ingest` and `feed`, each with a DLQ (`maxReceiveCount = 5`) and a DLQ-depth alarm. Separate queues keep a backfill from starving feed recomputes.
- Messages: `reconcile.tick`, `source.poll{source_id}`, `item.stage{content_item_id, stage, expected_rev}`, `review.apply{decision_id}`, `feed.recompute{user_id, reason}`. Each carries an idempotency key (LOAD-5).
- Chaining: the runner loads the item, applies the rights gate, runs the stage, writes outputs and advances `stage` with `WHERE rev = expected_rev` in one transaction, then sends the next message. A stage the profile forbids is skipped; a metadata-only source goes from discover to store.
- Retries: transient errors are redelivered by SQS with backoff. Permanent errors set `status = failed` with a reason and ack. Over budget sets `status = deferred_budget`; `tick` re-enqueues after reset.
- Runs twice: the compare-and-set matches no row, so the message is acked with no effect. Outputs are idempotent too: raw HTML at `raw/{item}/{sha256}` in S3, moment IDs from `hash(item, heading_path, ordinal)` with upsert, `ai_output` unique on `(kind, subject, prompt_version)`.
- Crash after commit, before send: `tick` finds the item in a non-terminal stage with an old `updated_at` and re-enqueues it. Chosen over a transactional outbox as one fewer moving part.
